## フェーズ1: コードレビューと修正（コミット `c366e1f`）

### やったこと

| 変更 | 考え方 |
|---|---|
| CLI引数化（`--language` `--persona` `--model` `--interval` `--timeout` `--lm-studio-url` `--no-tts`） | 設定を変えるたびに `race_engineer.py` を直接編集させるのはユーザー体験として悪い。`argparse` でモジュール冒頭の定数を上書きできるようにし、固定運用したい人は従来通りコードを書き換える選択肢も残した（後方互換） |

| `tests/test_tts_engine.py` 新規作成 | 直前のセッションでTTS機能（`tts_engine.py`）が追加されていたが、テストが一切なかった。音声ハードウェアが無い環境でも検証できるよう、Voicevoxへの HTTP 呼び出しはモックし、「TTSが失敗してもメインループを絶対に止めない」という契約を中心にテストを書いた |
| `requirements-dev.txt` 追加、READMEにテスト手順を追記 | `pytest` がどの依存関係リストにも書かれておらず、テストの存在自体がREADMEに書かれていなかった。実行不能に近い状態だったため追加 |

## フェーズ2: 効率改善の深堀り（コミット `0f7e161`）

「効率を良くしよう」という抽象的な指示に対して、まず実際のボトルネックがどこにあるかを推測ではなく一次資料で確認した。`docs/superpowers/specs/2026-06-29-tts-design.md` を読み返すと、TTS再生は「直列（同期）。読み上げ完了後に次のループへ進む」と明記されていた。

つまり実際のループ周期は

```
INTERVAL_SEC + LLM応答時間 + TTS合成/再生時間
```

であり、公称10秒よりも大きく伸び得る。これが体感的な「動作効率」の劣化要因だと判断した。

### 動作効率（ランタイム）

- **`tts_engine.speak_async()` を新規追加**。バックグラウンドのワーカースレッド1本が容量1のキューを消費して直列に再生する（複数音声が重ならないようにするため、キューは1本だけ）。メインループは音声再生の完了を待たずに次のテレメトリ取得へ進める。
- ワーカーがまだ前の発話を再生中に新しい指示が来た場合、キュー内の未消費メッセージを新しいものに差し替える。無線指示は鮮度が命なので、古い指示を溜め込んで後から喋るより、常に最新のテレメトリに基づく指示を優先する設計にした。
- 同期版 `speak()` はそのまま残し、`speak_async()` はその薄いラッパーとして実装（エラー握りつぶしのロジックを二重実装しないため）。
- 設計変更の経緯を、削除・書き換えではなく既存の設計ドキュメントへの「Addendum」として追記し、意思決定の履歴を残した。

### 作業効率（開発）

- **CIが一切存在しなかった。** 前セッションで追加したテストスイートも「手動で `pytest` を叩かない限り誰も気づかない」状態だった。`.github/workflows/tests.yml` を追加し、push/PRごとにPython 3.9 / 3.12の2系統でテストが自動実行されるようにした。
- **依存関係の分離。** `requirements.txt` に `kokoro`（内部でtorch系の重いMLライブラリに依存）が含まれており、テストを回すだけ、あるいは音声出力が不要なユーザーにも重いインストールを強制していた。`requirements.txt`（コア: openaiのみ）と `requirements-tts.txt`（音声関連の任意インストール）に分割。CIも軽量な方だけをインストールすることで高速化・安定化した。
- TTSのセットアップ手順がREADMEに一切書かれていなかったため、両言語版に追記。

### 見送った項目とその理由

- **`rf2_reader.py` が `read_snapshot()` 毎回（10秒ごと）に共有メモリのハンドルを開閉している点。** 理論上は開きっぱなしにする方が効率的だが、(1) 10秒間隔に対してオーバーヘッドは無視できるレベルであること、(2) Windows専用のAPI（`mmap` の `tagname` 引数）でこのLinuxサンドボックス上では動作検証ができないこと、の2点から、確信の持てない変更を入れるリスクの方が大きいと判断し、あえて手を付けなかった。
